# AEngine 信息链路要素体系与理论框架

**日期:** 2026-03-28  
**用途:** 为当前架构重构提供一套可解释、可落地、可验证的信息链路理论基础。  
**核心目标:** 让“为什么这样拆字段、为什么这样分模块、为什么某些判断交给代码而不是交给 LLM”拥有统一依据。

---

## 1. 核心命题

对 AEngine 这类“受控叙事系统”来说，稳定性不是由某一个 Prompt 的质量决定的，而是由**信息链路中的各类要素是否被正确区分、正确传递、正确落地**决定的。

系统要想在 50 回合内保持叙事稳定，至少要满足三件事：

1. **事实不漂移**
   - 结构化真值不能被自然语言反向篡改
   - 过去已经结算的结果不能在下游被重写

2. **因果不丢失**
   - 当前回合内已发生但尚未合并的事件，必须能被后续步骤继续读取
   - 同回合多 NPC 之间必须共享同一条临时链路

3. **记忆不断裂**
   - 长期叙事记忆、对话记忆、持久化恢复后的上下文必须能重新进入推理链

因此，本次重构的对象不是“Prompt 文案”，而是**从玩家输入到最终记忆提交之间的整条信息链路**。

---

## 2. 信息链路的三维理论

为了让链路要素体系化，本框架从三个维度定义信息：

### 2.1 存在论维度：这条信息“是什么”

信息在系统中不是同一种东西，而应分成不同本体类型：

1. **世界事实**
   - 角色位置、物品归属、数值状态、地图连接
   - 由 `GameState` 表示

2. **输入信号**
   - 玩家说了什么，NPC说了什么
   - 是原始表达，不是系统解释

3. **意图解释**
   - 系统把原始输入理解成了什么动作、什么对话意图

4. **规则结算事实**
   - 是否需要检定、使用什么检定、检定结果是什么

5. **步骤结算结果**
   - 某一步实际发生了什么、产生了哪些状态变更、局部叙事是什么

6. **回合因果链**
   - 当前回合已经发生的步骤及其顺序关系

7. **叙事投影**
   - 对外展示给玩家的合并叙事文本

8. **长期记忆**
   - 后续推理需要读取的摘要、对话立场、关键事实

9. **持久化投影**
   - 为存档恢复而保存的状态与记忆快照

如果一个字段同时承载了以上多种本体，它几乎一定会失稳。

---

### 2.2 时间论维度：这条信息“活多久”

不同信息的生命周期不同：

1. **瞬时信息**
   - 只在某一步调用内有效
   - 例如原始输入、临时提示

2. **回合内信息**
   - 只在当前回合有效，但需要被后续步骤继续读取
   - 例如玩家检定结果、NPC1 的即时反击结果

3. **近期记忆**
   - 最近数回合中高频会被使用的上下文
   - 例如最近几轮对话、最近事件摘要

4. **长期记忆**
   - 跨 10-50 回合仍需稳定保留的故事事实、立场变化、承诺关系

5. **持久记忆**
   - 需要写入存档并在读档后恢复的内容

如果一个字段同时试图承担“回合内临时链路”和“长期记忆”，它最终往往两边都做不好。

---

### 2.3 权威论维度：这条信息“谁说了算”

系统中的信息必须有明确的权威来源：

1. **代码权威**
   - 最终由代码裁定
   - 例如实体存在性、字段合法性、候选 NPC 列表、检定枚举、事务落地

2. **代码校验的 LLM 结果**
   - 可以由 LLM 生成，但必须经代码验证后才能进入链路
   - 例如 `TurnIntent`、`NpcActionPlan`、`StateChange`

3. **LLM 建议型信息**
   - 只作为候选，不直接当事实
   - 例如 NPC 激活建议、对话语气判断

4. **展示型自然语言**
   - 不具有事实定义权
   - 例如 `merged_narrative`

如果一段自然语言同时被当作“展示文本”和“事实来源”，长期必然漂移。

---

## 3. 信息链路九要素模型

在上述三维理论基础上，建议将系统中的信息链路收敛为九个核心要素。

## 3.1 E1：世界事实（World Truth）

**回答的问题：** 世界现在客观上是什么样。  
**当前代表：** `GameState`  
**权威来源：** 代码  
**生命周期：** 长期 + 持久化  
**允许谁修改：** 只能通过事务化状态变更链修改

**职责边界：**
- 是唯一结构化真值
- 不携带叙事修辞
- 不直接承载 Prompt 专用说明

---

## 3.2 E2：输入信号（Input Signal）

**回答的问题：** 玩家或 NPC 原话是什么。  
**建议字段：**
- `raw_input_text`
- `utterance_text`

**权威来源：** 用户输入 / 系统原始记录  
**生命周期：** 至少回合内保留，可写入对话记忆  
**作用：**
- 保留语言细节、代词、语气、修辞
- 为 DM 的意图解释提供原文依据

**为什么不能删除：**
- 原始输入和系统解释不是同一件事

---

## 3.3 E3：意图解释（Intent Interpretation）

**回答的问题：** 系统把原始输入理解成了什么。  
**建议对象：** `TurnIntent`

建议最小结构：

```json
{
  "actor_id": "char-player-01",
  "raw_input_text": "我要攻击守卫",
  "intent_text": "玩家试图攻击守卫",
  "interaction_type": "action/dialogue/mixed",
  "check_plan": {...},
  "activation_hint": {...}
}
```

**权威来源：** LLM 生成，代码校验  
**生命周期：** 当前回合  
**作用：**
- 作为规则系统和执行层的输入契约
- 保留“原话”和“解释”之间的差异

**当前系统的问题：**
- `action_description` 同时扮演原话替身和解释结果，职责过重

---

## 3.4 E4：规则结算事实（Rule Resolution Fact）

**回答的问题：** 规则层最终怎么裁定。  
**建议对象：**
- `CheckPlan`
- `CheckResult`

**权威来源：** 代码  
**生命周期：** 回合内，必要时写入回合链  
**作用：**
- 将“需要检定什么”与“检定结果是什么”明确分离
- 作为所有后续链路的事实锚点

**重构含义：**
- 检定结果必须是代码权威，不应由后续叙事重写

---

## 3.5 E5：步骤结算（Step Resolution）

**回答的问题：** 某一步真正发生了什么。  
**建议对象：** `TurnResolution`

建议结构：

```json
{
  "actor_id": "char-player-01",
  "phase": "player/npc",
  "intent_text": "...",
  "check_result": {...},
  "state_changes": [...],
  "local_narrative": "...",
  "outcome": {
    "action_succeeded": true,
    "check_outcome": "成功"
  }
}
```

**权威来源：**
- 检定事实由代码提供
- 局部叙事和变更候选由 LLM 生成，代码验证后入链

**生命周期：** 当前回合，可短期持久化  
**作用：**
- 将“一个角色的一步”完整封装
- 让后续 NPC 和 NarrativeMerger 读取的是步骤级对象，而不是零散字段

**当前系统的问题：**
- `player_check_result`、`player_resolution_anchor`、`fragments`、`changes` 分散表达同一步信息

---

## 3.6 E6：回合因果链（Turn Trace）

**回答的问题：** 当前回合内已经发生了哪些步骤，它们之间如何因果相连。  
**建议对象：** `TurnTrace`

建议结构：

```json
{
  "turn_id": 12,
  "steps": [
    {"kind": "player_action", ...},
    {"kind": "npc_action", ...},
    {"kind": "npc_action", ...}
  ]
}
```

**权威来源：** 代码组装  
**生命周期：** 当前回合，必要时可保留最近若干回合摘要  
**作用：**
- 让 NPC2 看见 NPC1 刚刚做了什么
- 让 NarrativeMerger 面对完整因果链，而不是末端片段列表

**这是当前系统缺失的最关键要素。**

---

## 3.7 E7：叙事投影（Narrative Projection）

**回答的问题：** 玩家最后看到的叙事是什么。  
**建议对象：**
- `merged_narrative`
- `turn_summary`

**权威来源：** LLM 生成，但不具有结构化事实定义权  
**生命周期：** 展示后进入记忆提交阶段  
**作用：**
- 负责可读性、风格统一、文本压缩
- 不负责定义世界真值

**重构含义：**
- NarrativeMerger 的输出应视为“投影层”，不是“真值层”

---

## 3.8 E8：长期记忆（Memory Commit）

**回答的问题：** 下一回合推理时需要记住什么。  
**建议拆成两类：**

1. `DialogueMemory`
2. `NarrativeMemory`

**DialogueMemory** 应记录：
- 谁对谁说了什么
- 语气/立场/承诺变化
- 关键指代对象

**NarrativeMemory** 应记录：
- 最近事件摘要
- 关键事实
- 已合并的回合摘要

**权威来源：** 代码提交，内容可由 LLM 帮助压缩  
**生命周期：** 长期 + 持久化  
**作用：**
- 支撑 10-50 回合内的一致性

**当前系统的问题：**
- `dm_dialogue_log` 保存了，但不真正进入推理链
- `NarrativeContext` 既想当长期记忆，又想当短期链路

---

## 3.9 E9：持久化投影（Persistence Snapshot）

**回答的问题：** 哪些信息必须被保存，并在读档后恢复。  
**建议对象：**
- `GameStateSnapshot`
- `DialogueMemorySnapshot`
- `NarrativeMemorySnapshot`
- 最近若干回合 `TurnTraceDigest`

**权威来源：** 代码  
**生命周期：** 持久化  
**作用：**
- 让读档后不仅能“恢复世界状态”，还能“恢复可继续推理的记忆状态”

**当前系统的问题：**
- 只做到了“部分保存自然语言信息”
- 还没做到“恢复后重新进入完整推理链”

---

## 4. 字段合并、分离、删除的理论判据

有了九要素模型后，字段处理不应再凭直觉，而应有明确判据。

## 4.1 什么情况下应该合并字段

当两个字段同时满足以下条件时，应合并：

1. 表达的是同一种本体
2. 生命周期一致
3. 消费者基本一致
4. 其中一个只是另一个的展开形式

**当前典型例子：**
- `player_check_result` 与 `player_resolution_anchor` 中的检定事实部分  
  它们都属于 E4/E5 边界，且消费者高度重合，应合并成统一 `TurnResolution`

---

## 4.2 什么情况下应该分离字段

当一个字段同时承担以下中的两项及以上时，应分离：

1. 原始输入
2. 系统解释
3. 规则结算
4. 长期记忆
5. 展示叙事

**当前典型例子：**

### `action_description`
- 同时承担原始输入替身和解释结果
- 应拆为：
  - `raw_input_text`（E2）
  - `intent_text`（E3）

### `narrative_context`
- 同时承担长期叙事记忆和部分链路输入
- 应拆为：
  - `NarrativeMemory`（E8）
  - `TurnTrace`（E6）

---

## 4.3 什么情况下应该删除字段

当字段满足以下任一条件时，应删除：

1. 没有清晰的本体归属
2. 只是旧协议残留
3. 已被更高层对象完全覆盖
4. 其合法性无法被系统稳定解释

**当前候选：**
- `engine_context` 这类大包字段
- 已漂移 Prompt 中要求但模型中不存在的字段
- 只为兼容旧逻辑保留却不再进入主链路的字段

---

## 4.4 什么情况下必须交给代码而不是交给 LLM

凡是属于以下类型的字段，必须交给代码：

1. 合法性判定
2. 候选筛选
3. 枚举约束
4. 实体存在性
5. 事务一致性
6. 持久化同步

**例如：**
- `candidate_npc_ids`
- `check_target` 是否存在
- `difficulty` 是否有效
- `check_attributes` 是否在规则支持范围
- 状态变更的字段路径是否合法

LLM 可以参与建议，但不能拥有最终裁决权。

---

## 5. 逻辑主线：从输入到持久化的标准链路

重构后的标准逻辑主线应为：

### Step 1：接收原始输入

产出：
- `raw_input_text`

### Step 2：构造受控世界视图

产出：
- `WorldStateView`
- `DialogueMemoryView`
- `NarrativeMemoryView`

### Step 3：DM 解释输入

产出：
- `TurnIntent`

### Step 4：规则层裁定

产出：
- `CheckResult`

### Step 5：玩家阶段执行

产出：
- `TurnResolution`
- `TurnStep`
- 写入 `TurnTrace`

### Step 6：代码筛选需要行动的 NPC

产出：
- `activated_npc_ids`

### Step 7：Director 规划 NPC

输入：
- `TurnTrace so far`
- `NarrativeMemory`
- `WorldStateView`

产出：
- `NpcActionPlan[]`

### Step 8：逐个 NPC 执行

每个 NPC 执行后：
- 产出 `TurnResolution`
- 生成一个新的 `TurnStep`
- 立即写回 `TurnTrace`

### Step 9：叙事合并

输入：
- `TurnTrace`
- `turn_truth_anchor`
- `NarrativeMemory`

产出：
- `merged_narrative`
- `turn_summary`
- `new_key_facts`

### Step 10：记忆提交与持久化

提交到：
- `DialogueMemory`
- `NarrativeMemory`
- `GameState`
- `PersistenceSnapshot`

## 6. 为什么这套理论能保障重构合理

这套框架的价值在于，它把“重构为什么合理”从经验判断，提升为结构判断：

### 6.1 它解释了为什么当前会不稳定

因为当前系统缺的不是更长 Prompt，而是：
- E6 回合因果链缺失
- E8 长期记忆未正式进入推理链
- E2/E3/E5 混淆
- E7 被误当作事实来源

### 6.2 它为字段决策提供统一依据

以后不再争论“这个字段是不是看起来有用”，而要问：
- 它属于哪个要素？
- 生命周期是什么？
- 谁拥有权威？
- 是否已被上层对象覆盖？

### 6.3 它直接对应 50 回合稳定性目标

50 回合稳定性本质上依赖：

1. E1 世界事实稳定
2. E6 回合因果不断裂
3. E8 长期记忆能稳定提交
4. E9 读档后可恢复

如果这四项不成立，再好的 Prompt 也只能提高单回合表现，无法提高长期稳定性。

---

## 7. 对当前系统的直接判断

以九要素模型衡量，当前系统的状态是：

### 已具备

- E1 世界事实
- E4 规则结算
- E7 叙事投影
- E9 部分持久化

### 部分具备但混乱

- E3 意图解释
- E5 步骤结算
- E8 长期记忆

### 关键缺失

- E6 回合因果链

这就是为什么当前系统能做到：
- 单回合基本可运行
- 玩家阶段事实不易被改写

但做不到：
- 多 NPC 同回合稳定共享信息
- 10 次以上对话稳定延续
- 50 回合级别的高一致性叙事

---

## 8. 一句话总结

本次重构最根本的任务，是把当前系统从“字段与 Prompt 松散拼接的流水线”，升级为“以九要素模型组织、由代码维护链路、由 LLM 参与解释和表达的受控叙事系统”。

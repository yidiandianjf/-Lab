# AEngine 重构计划大纲（稳定性导向）

**日期:** 2026-03-28  
**适用范围:** 当前 `src/` 主链路、`prompt/` 提示词、`docs/review/` 中已识别问题  
**目标:** 以“叙事稳定性、链路一致性、可落实性、可维护性”为核心，重构当前 DM -> StateEvolution -> NPCDirector -> NarrativeMerger -> NarrativeContext/持久化 的调用链。

---

## 0. 设计背景

结合以下审查文档与交流结论：

- `docs/review/llm_context_analysis.md`
- `docs/review/research_code_vs_llm_tasks.md`
- `docs/review/review_state_evolution_npc_role.md`
- `docs/review/npc_response_mode_analysis.md`
- `docs/review/narrative_stability_context_chain_review.md`
- `docs/review/信息链路要素体系与理论框架.md`
- `docs/review/完整Review总结.md`

当前系统已经具备：
- 基本可运行的玩家主流程
- 玩家阶段事实锚点
- NPC 后置响应能力
- NarrativeContext 压缩记忆
- 存档/读档基础能力

但仍存在以下根本问题：

1. 同一事实在多个模块中被重复表达，字段职责漂移。
2. 长期记忆、临时链路、结构化真值、展示叙事混杂在一起。
3. `DM`、`StateEvolution`、`NPCDirector`、`NarrativeMerger` 没有共享统一的事实协议。
4. 同回合多 NPC 之间无法共享即时链路结果。
5. 持久化保存了部分自然语言信息，但并未全部重新进入推理链。
6. Prompt 与代码协议开始漂移，继续堆补丁会放大历史债。

因此，本次重构不是“优化提示词”，而是**重构整个信息链路与协议边界**。

### 0.1 本次重构的逻辑主线

本次重构不是从“模块名”出发，而是从“信息在系统中的流动方式”出发。

逻辑主线如下：

1. 玩家输入的是**原始信号**
2. DM 将原始信号解释为**意图**
3. 规则系统将意图转化为**结算事实**
4. 玩家/NPC 执行层将结算事实转化为**步骤结果**
5. 多个步骤组成当前回合的**因果链**
6. 叙事层将因果链投影为**展示叙事**
7. 记忆层将展示叙事与关键事实压缩为**长期记忆**
8. 持久化层保存世界状态、长期记忆与必要链路摘要

也就是说：

`输入信号 -> 意图解释 -> 规则结算 -> 步骤结果 -> 回合因果链 -> 叙事投影 -> 记忆提交 -> 持久化投影`

如果这条主线中任一环节的本体、生命周期或权威来源不清晰，就会表现为：
- 字段重复
- Prompt 漂移
- 多 NPC 同回合链路断裂
- 长对话一致性不足
- 读档后“状态恢复了，但记忆没恢复”

### 0.2 理论依据

本计划以 [`信息链路要素体系与理论框架.md`](./信息链路要素体系与理论框架.md) 为理论基础。

该框架将系统信息分为九个要素：

1. 世界事实（World Truth）
2. 输入信号（Input Signal）
3. 意图解释（Intent Interpretation）
4. 规则结算事实（Rule Resolution Fact）
5. 步骤结算（Step Resolution）
6. 回合因果链（Turn Trace）
7. 叙事投影（Narrative Projection）
8. 长期记忆（Memory Commit）
9. 持久化投影（Persistence Snapshot）

本次所有字段合并、字段拆分、Prompt 收敛、持久化重做，都必须能回扣到这九类要素中的某一类；如果回扣不上，就说明该字段或逻辑没有明确存在意义。

## 1. 重构约束

本次重构必须遵守以下硬约束：

### 1.1 真值约束

1. `GameState` 仍然是唯一结构化世界真值。
2. 自然语言叙事永远不能反向定义结构化状态。
3. LLM 只能解释、生成、补全，不得拥有字段合法性与实体存在性的最终裁决权。

### 1.2 链路约束

1. 玩家输入到最终叙事之间，必须存在一条可追踪、可持久化、可调试的结构化链路。
2. 同回合多步事件必须共享统一的临时链路对象，不能只靠文本摘要传递。
3. 长期记忆与同回合临时链路必须分离。

### 1.3 兼容约束

1. 迁移期间允许兼容层存在，但兼容层不得继续承载新功能。
2. 新协议必须通过适配器逐步接入，不能一次性在所有模块同时改写。
3. 存档格式变化必须带版本号和恢复策略。

### 1.4 工程约束

1. 重构应按阶段落地，每阶段必须能单独验证。
2. 每引入一个新数据结构，必须明确：
   - 来源
   - 消费者
   - 持久化边界
   - 生命周期
3. Prompt 改动必须跟随协议改动，不允许只靠“补 prompt”掩盖链路问题。
4. 不允许继续扩大历史遗留字段与废弃流程入口。

### 1.5 稳定性约束

1. 目标不是“更聪明”，而是“50 回合内更稳定”。
2. 优先保证一致性与可解释性，再追求信息丰富度。
3. 长对话一致性、同回合因果一致性、读档后记忆一致性，必须优先于叙事华丽度。

## 2. 重构哲学

本次重构遵循以下设计哲学：

### 2.1 事实归代码，表达归 LLM

- 代码负责：实体合法性、候选筛选、检定枚举、持久化同步、链路组装、事务边界。
- LLM 负责：意图解释、行动语义表达、NPC意图生成、局部叙事生成、叙事合并与记忆压缩建议。

### 2.2 先协议，后 Prompt

先统一数据结构和链路责任，再改 Prompt。  
Prompt 是协议的解释层，不是协议本身。

### 2.3 先结构化链路，后自然语言压缩

长期可维护的系统必须先有结构化 `turn_trace`，再把它压缩成 `narrative_context`。  
不能反过来依赖摘要文本还原因果。

### 2.4 一件事实只表达一次

同一事实只应保留一个权威字段，避免：
- `player_check_result` / `player_resolution_anchor` 双份表达
- `inventory` / `inventory_details` 双份表达
- `player_intent` 整包复用带来的协议污染

### 2.5 兼容层隔离，不反向污染主流程

迁移期保留的旧入口、旧字段、旧 Prompt 只能作为适配边界，不得继续成为主链路的一部分。

### 2.6 为 50 回合稳定性设计，而不是为单回合演示设计

系统必须优先回答：
- 10 轮以上对话是否能保持角色立场稳定
- 50 回合后是否还能保持因果链不断裂
- 读档后是否仍能沿同一条记忆链继续推理

## 3. 落实方向

本次重构的落实方向分为六个面：

### 3.1 协议统一

为 DM / StateEvolution / NPCDirector / NarrativeMerger 设计统一协议对象，减少同义字段和临时拼贴字段。

### 3.2 上下文分层

将上下文明确拆成四层：

1. `world_state_view`
2. `dialogue_memory`
3. `turn_trace`
4. `narrative_memory`

### 3.3 输出收敛

让玩家阶段与 NPC 阶段尽量复用同一类输出结构，而不是一套 `DMAgentOutput`、一套 `NPCActionDecision`、一套 `StateEvolutionOutput` 各自演化。

### 3.4 持久化重做

将可持续影响推理的自然语言信息纳入正式持久化边界，而不是仅作为“保存但不消费”的附属字段。

### 3.5 Prompt 去遗留

删除已漂移字段、废弃示例、注释型修改建议，重写 Prompt 输入说明与强约束。

### 3.6 验证闭环

把“50回合稳定”拆成可测试目标：
- 长对话一致性
- 多 NPC 同回合因果一致性
- 读档后记忆延续性
- 叙事与状态不脱钩

## 4. 目标架构轮廓

建议引入以下核心数据对象：

### 4.1 `WorldStateView`

用于向 LLM 暴露受控、裁剪后的世界视图，而不是直接散装拼接 `engine_context`。

建议包含：
- 当前地图
- 当前场景角色
- 当前场景物品
- 玩家状态
- 必要的邻接与目标信息

### 4.2 `DialogueMemory`

用于记录长期对话记忆，不再让 `dm_dialogue_log` 成为“只保存不消费”的悬空数据。

建议包含：
- speaker
- addressee
- utterance
- dialogue_act
- referenced_entities
- stance_update
- turn

### 4.3 `TurnIntent`

替代当前单一 `action_description` 概念，拆分为：
- `raw_input_text`
- `intent_text`
- `interaction_type`
- `check_plan`
- `activation_hint`

### 4.4 `TurnResolution`

统一玩家阶段与 NPC 阶段的“检定 + 临时叙事 + 变更 + 成败结果”表达。

### 4.5 `NpcActionPlan`

保留结构化计划，但收敛输入输出边界，只保留 Director 真正需要和真正负责的字段。

### 4.6 `TurnStep`

一条回合内步骤记录，既可表示玩家动作，也可表示单个 NPC 动作。

### 4.7 `TurnTrace`

本回合所有步骤的结构化总线。  
这是本次重构的关键对象。

### 4.8 `NarrativeMemory`

替代当前语义模糊的 `narrative_context`，明确它是长期叙事摘要层，而非临时链路层。

## 5. 重构步骤

建议按 8 个阶段推进。

## Phase 0：冻结现状与不变量

### 目标

在重构前先明确系统当前必须保住的运行不变量。

### 输出

1. 不变量清单
   - `GameState` 为唯一结构化真值
   - 检定结果不能被叙事改写
   - 状态变更必须走统一事务链
   - 读档后世界状态、叙事记忆、对话记忆应可恢复
2. 当前活跃主链路文档
3. 遗留入口清单

### 关键文件

- `src/engine/game_engine.py`
- `docs/spec/runtime_detailed_spec.md`
- `docs/review/完整Review总结.md`

---

## Phase 1：定义新协议与核心数据结构

### 目标

先把新协议建出来，不直接改业务逻辑。

### 输出

新增模型：
- `TurnIntent`
- `CheckPlan`
- `TurnResolution`
- `TurnStep`
- `TurnTrace`
- `DialogueMemorySnapshot`
- `NarrativeMemorySnapshot`
- `NpcActionPlanV2`

### 重构要点

1. `action_description` 不直接删除，拆为：
   - `raw_input_text`
   - `intent_text`
2. `player_check_result` 与 `player_resolution_anchor` 合并到 `TurnResolution`
3. `recent_events` 与 `narrative_context` 不再承担同一职责

### 关键文件

- `src/data/models.py`
- `src/data/npc_planning_models.py`

---

## Phase 2：拆分上下文构建器

### 目标

把当前分散在 `GameEngine` 里的上下文拼贴逻辑抽离。

### 输出

新增构建器：
- `WorldStateViewBuilder`
- `DialogueMemoryBuilder`
- `NarrativeMemoryBuilder`
- `TurnTraceContextBuilder`
- `NpcPlanningContextBuilder`

### 重构要点

1. 删除 `engine_context` 这种泛用大包字段
2. 每个 Agent 只收到自己能理解的上下文对象
3. 每个上下文字段都必须有用途说明

### 关键文件

- `src/engine/game_engine.py`
- 新增 `src/context/` 或 `src/engine/context_builders.py`

---

## Phase 3：重构 DM 层为“路由器+解释器”

### 目标

收缩 DM 的职责，不再让它成为链路事实生产者。

### 输出

DM 输出改为：
- `TurnIntent`
- 可选 `response_to_player`
- 不再整包承担下游 NPC 决策字段

### 重构要点

1. `candidate_npc_ids` 由代码决定，DM 只提供激活提示
2. `npc_response_needed` 可以转为可选建议，不再作为唯一事实开关
3. 正式接入 `DialogueMemory`
4. 对话历史改为结构化，而不是简单字符串拼接

### 关键文件

- `src/agent/dm_agent.py`
- `src/agent/prompt/system_prompt.md`

---

## Phase 4：重构玩家阶段执行链

### 目标

让玩家阶段产出的不是零散字段，而是标准化的 `TurnStep`。

### 输出

玩家阶段流程：

`raw_input_text -> TurnIntent -> CheckPlan -> CheckResult -> TurnResolution -> TurnStep`

### 重构要点

1. 玩家 `StateEvolution` 输入改为：
   - `world_state_view`
   - `dialogue_memory`
   - `narrative_memory`
   - `turn_trace_so_far`
   - `turn_intent`
2. 玩家阶段输出 `TurnStep`
3. 该 `TurnStep` 立即写入 `TurnTrace`

### 关键文件

- `src/agent/state_evolution.py`
- `src/engine/game_engine.py`

---

## Phase 5：重构 NPCDirector 与 NPC 执行链

### 目标

让 Director 真正基于统一链路上下文规划，并让多个 NPC 在同回合内共享即时结果。

### 输出

NPC 阶段流程：

`TurnTrace -> NpcActionPlan[] -> NPC Check -> NPC TurnStep -> TurnTrace 追加`

### 重构要点

1. Director 输入不再是整个 `DMAgentOutput`
2. Director 输入应包含：
   - `activated_npc_ids`
   - `turn_trace_so_far`
   - `narrative_memory`
   - `npc_world_views`
3. 每个 NPC 执行后，先写入 `TurnTrace`
4. 下一个 NPC 读取更新后的 `TurnTrace`

### 关键文件

- `src/agent/npc/npc_director.py`
- `src/agent/prompt/npc_director_prompt.md`
- `src/engine/game_engine.py`

---

## Phase 6：重构叙事合并与记忆提交

### 目标

让 NarrativeMerger 面对的是完整回合链，而不是零散片段列表。

### 输出

叙事层输入改为：
- `turn_trace.steps`
- `turn_truth_anchor`
- `narrative_memory`

叙事层输出：
- `merged_narrative`
- `turn_summary`
- `new_key_facts`

### 重构要点

1. NarrativeMerger 不只合并文本，还应输出可提交给记忆层的摘要结果
2. 叙事合并完成后，统一提交到：
   - `NarrativeMemory`
   - `DialogueMemory`（如涉及对话立场变化）
3. 将“叙事落地”从“仅保存文本”升级为“更新长期记忆”

### 关键文件

- `src/narrative/narrative_merger.py`
- `src/narrative/narrative_context.py`
- `src/narrative/prompt/narrative_merger_prompt.md`

---

## Phase 7：重构持久化边界

### 目标

正式把对推理有意义的数据纳入持久化协议。

### 输出

持久化对象至少包括：
- `GameState`
- `DialogueMemory`
- `NarrativeMemory`
- 最近 N 回合 `TurnTrace` 摘要
- `save_version`

### 重构要点

1. 存档不再只保存“能显示的东西”，还要保存“能继续推理的东西”
2. 增加版本化迁移器
3. 明确读档后哪些上下文必须立即可用

### 关键文件

- `src/data/io_system.py`
- `src/engine/game_engine.py`

---

## Phase 8：Prompt 收敛与遗留清理

### 目标

在新协议稳定后，清理所有历史遗留字段和 Prompt 漂移。

### 输出

1. 删除 Prompt 中的：
   - `#修改建议`
   - 非法 JSON 示例
   - 已废弃字段说明
2. 删除或封存旧入口：
   - `_process_npc_turns_until_player()`
   - `_process_reactive_npc_response()`
   - 其他仅用于迁移期的旧逻辑

### 重构要点

1. Prompt 只描述新协议，不保留旧字段兼容说明
2. 兼容层只保留在适配器中，不保留在 Prompt 里

---

## 6. 重构要点

以下是本次重构过程中最关键的实施要点：

### 6.1 字段层

1. 拆分 `action_description`
2. 合并 `player_check_result` 与 `player_resolution_anchor`
3. 减少 `player_intent` 整包传递
4. 去掉 `engine_context` 式大包字段
5. 明确 `narrative_context` 与 `recent_events` 的职责边界

### 6.2 上下文层

1. 长期记忆和临时链路绝不混用
2. 同回合多 NPC 必须共享 `TurnTrace`
3. `DialogueMemory` 必须真正进入推理链

### 6.3 Prompt 层

1. Prompt 输入必须和数据协议一一对应
2. 每个字段必须解释：
   - 是事实还是提示
   - 是强约束还是建议
   - 可不可以被改写
3. Prompt 不能再承担兼容层说明

### 6.4 持久化层

1. 保存后必须能恢复继续推理所需的上下文
2. 读档后不能只恢复展示文本，必须恢复长期记忆状态
3. 存档结构必须版本化

### 6.5 测试层

本次重构必须建立以下回归测试：

1. 10轮以上玩家-NPC 对话一致性测试
2. 多 NPC 同回合因果传递测试
3. 50 回合 NarrativeMemory 漂移测试
4. 读档后继续推理一致性测试
5. Prompt 协议字段完整性测试

---

## 7. 非目标

为了避免重构范围无限膨胀，本次明确以下内容不是第一阶段目标：

1. 不追求一次性重写整个项目
2. 不优先追求 Web/API 层改造
3. 不先处理美术、CLI体验、前端展示问题
4. 不先做复杂世界观编辑器
5. 不把“更长上下文”误当成“更稳定架构”

---

## 8. 验收标准

本次重构完成后，至少应满足：

### 8.1 链路一致性

1. 玩家阶段事实能稳定传到 Director、NPC 执行层、NarrativeMerger
2. 同回合后续 NPC 能读取前序 NPC 的临时结果
3. NarrativeMerger 面对的是完整回合链而不是零散片段

### 8.2 长期稳定性

1. 10 轮以上对话能保持角色立场与称谓基本稳定
2. 50 回合内 NarrativeMemory 不出现大面积事实漂移
3. 读档后继续 10 回合推理不出现明显断层

### 8.3 工程可落实性

1. 每阶段都可单独合并
2. 旧协议可以通过适配器过渡
3. Prompt 与代码协议不再互相漂移

---

## 9. 一句话总结

这次重构的核心，不是“把 Prompt 写得更聪明”，而是把当前系统从“多个 LLM 模块松散串联”重构成“一条由代码显式维护、LLM按统一协议参与的稳定信息链”。
